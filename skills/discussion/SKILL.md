# discussion — 複数LLMディスカッション

1つの議題 (方針・設計判断・意見が割れる問い) に対し、複数LLMが**独立に意見を出し、対立点をぶつけ合い、モデレータが裁定して1つの成果物に集約する**。fusion-review が「同じ依頼を並列に1回投げて統合する」のに対し、discussion は反論のラウンドを挟んで意見の当否を詰める。

**モデレータはこのセッションのLLM自身**。llms.json に載るのは討論者 (モデレータ以外) だけで、`schema: self` は使わない。集約・裁定・問いの投入はモデレータが行い、多数決では決めない。

## 設定ファイル (有効LLMの管理)

有効なLLMの一覧は**このスキルディレクトリの `llms.json`** で管理する:

- 原本: `<repo>/skills/discussion/llms.json` (CodingAgentTools レポ、Git管理)
- 実行時パス: `~/.claude/skills/discussion/llms.json` (make setup-skills のシンボリックリンク経由で同一実体)

| フィールド | 意味 |
|-----------|------|
| `name` | 短い識別子。中間成果物のファイル名や map.md の参加者名に使う |
| `label` | モデルの説明 (人間向け)。最終出力のメタ情報検査にも使う |
| `enabled` | `true` のものだけ討論者にする。無効化はここを `false` にするだけ |
| `schema` | `stdin` のみ (下表) |
| `command` | 起動コマンド |
| `timeout_ms` | 実行時のタイムアウト。shell の `timeout` コマンドに秒換算で渡す |
| `notes` | モデルの特性・注意点 |

| schema | 実行方法 |
|--------|---------|
| `stdin` | 任意コマンド。`command` をそのまま実行し、stdin にプロンプト・stdout に回答 |

討論者は OpenCode に統一する。追加は llms.json にエントリを1つ足すだけで、`schema: "stdin"` + `command: "opencode run --model <provider>/<id> --agent plan"` を書く (`--agent plan` が read-only を担保する)。使えるモデルは `opencode models` で確認し、無ければ configs.jsonc に足して `make opencode-global` を回す。編集はレポ側のファイルに対して行い、コミットする (シンボリックリンクなのでどちらのパスを編集しても実体は同じ)。

## 実行手順

### 1. 設定を読む

`~/.claude/skills/discussion/llms.json` を Read し、`enabled: true` のLLMだけを討論者にする。0個ならその旨を伝えて終了する。討論者が1人でも進行するが、対立が構造的に生まれないため「討論」ではなく単独意見の整理になる。

### 2. 議題を決める

引数、または会話の文脈から議題を決める。曖昧で文脈からも定まらない場合はユーザーに確認する。議題は1つの問いの形に定式化する (例: 「〜を採用すべきか」「AとBのどちらが良いか」)。論点の細分化は1周目の意見を見てから行うので、最初は議題1つでよい。

### 3. 環境を整える

対象がリポジトリのコード・設計なら、参加者が全体を読めるように worktree を用意する (概念の議論・方針の話ならスキップ):

```bash
# PRモード: PR head を worktree に取り出す
git fetch origin pull/<N>/head
git worktree add --detach <tmp>/discussion-wt FETCH_HEAD

# ローカルモード: HEAD の worktree に未コミット差分を適用する
git worktree add --detach <tmp>/discussion-wt HEAD
git diff HEAD | git -C <tmp>/discussion-wt apply
git ls-files --others --exclude-standard | while read -r f; do
  mkdir -p "<tmp>/discussion-wt/$(dirname "$f")" && cp "$f" "<tmp>/discussion-wt/$f"
done
```

成果物は tmp (セッションの scratchpad、なければ `/tmp`) の同じディレクトリに平置きする:

| ファイル | 内容 |
|----------|------|
| `r1-prompt.md` | 1周目の共通プロンプト |
| `r1-<name>.md` | 1周目の回答 (討論者ごと) |
| `map.md` | 論点マップ (モデレータの中間成果物) |
| `r2-prompt-<name>.md` / `r2-<name>.md` | 2周目の個別プロンプトと回答 |
| `draft.md` | 集約案 (モデレータの中間成果物、3周目の入力) |
| `r3-prompt.md` / `r3-<name>.md` | 3周目の共通プロンプトと回答 |
| `conclusion.md` | 最終成果物 |
| `err-<round>-<name>.log` | 失敗した討論者の stderr |

### 4. ラウンドの回し方 (共通形)

**外部LLMは1つの Bash 呼び出しにまとめず個別に** `run_in_background: true` で起動し、全員の起動を済ませてから完了を待つ (逐次実行しない):

```bash
# worktree がある場合は cwd にして起動する (リポジトリ探索を可能にする)
cd <tmp>/discussion-wt && cat <tmp>/r1-prompt.md | timeout <timeout_ms/1000>s <command> > <tmp>/r1-<name>.md 2> <tmp>/err-r1-<name>.log
```

- 回答は中間成果物として1ファイルずつ吐き出す。ファイル名はラウンドと `name` を組み合わせる
- タイムアウトは llms.json の `timeout_ms` を shell の `timeout` コマンド (秒に換算) で強制する。Bash ツールの `timeout` パラメータは上限 10 分で `timeout_ms` がそれを超えうるため、ツール側ではなく shell 側で制御する
- 失敗・タイムアウト・空出力の討論者は**リトライせずスキップ**する。全員が揃うまで次のラウンドに進まない (ラウンドは本質的に逐次)
- あるラウンドの回答が0件になったら `err-*.log` を添えて報告し、続行可否を判断する。1周目で0件なら終了する

### 5. 1周目 — 独立意見 (flat)

他の参加者の意見に触れていない状態の立場を集める。**モデレータの考えをプロンプトに混ぜない** (独立性の担保)。

`<tmp>/r1-prompt.md`:

```markdown
あなたはある議題について意見を求められた独立した参加者です。他の参加者の意見は見えていません。追従せず、自分の立場を明確にしてください。

# 議題
<議題 (問いの形)>

コードは <worktree絶対パス> にチェックアウト済み。必要な範囲で読んで判断してよい (読み取りのみ。ファイルを変更しない)。

# 答えてほしいこと
1. 結論 (端的に)
2. 根拠
3. その結論が依存する前提・仮定
4. 自信の度合い (高/中/低) と、自信を下げる要因
5. 自分が間違っているとしたら、どこが間違いやすいか

上記 1-5 の見出しで簡潔に。
```

### 6. 論点マップ (`map.md`) — 1周目の整理

全員の `r1-<name>.md` を読み、**意見をまとめない**。論点 (評価軸) ごとに、誰が同じことを言い、誰が対立し、誰が別のことを言っているかという関係だけを整理する:

```markdown
# 論点マップ (中間成果物)
## 論点 (評価軸): <問い>
- 立場1: <内容> — 参加者: <name, ...>
- 立場2: <内容> — 参加者: <name, ...>
- 対立の核心: 事実認識の違い / 価値判断の違い / 前提の違い のどれか
- 一致している点: ...
- 未検証の前提: ...
- どの立場も触れていない観点: ...

## モデレータの疑問・反論 (2周目に投げる候補)
- <疑問 / 反論>
```

- 「同一意見」「反対意見」「矛盾しないが異なる意見」を区別する。反対でないものを対立扱いしない
- 2周目以降のプロンプトでは参加者を匿名ラベル (参加者A, B, ...) で示す。実名はこの map.md にだけ書く (ブランドへの権威追従を防ぐ)
- ここで合意形成をしない。map.md は2周目の入力であり、最終出力には使わない

### 7. 2周目 — 食い違いへの応答

各参加者に個別のプロンプトを作る。**論点マップで対立・相違が確認できた意見 (匿名) と、モデレータ自身の疑問・反論**を渡す:

`<tmp>/r2-prompt-<name>.md`:

```markdown
あなたを含む複数の参加者が同じ議題に答えました。あなたの1周目の立場は次の通りです:
<1周目の要約>

# 食い違っている点
## 論点: <...>
- あなたの立場: <...>
- 参加者Aの立場: <内容> (根拠: <...>)
- 参加者Bの立場: <内容> (根拠: <...>)

# モデレータからの問い (結論の誘導ではなく、判断材料の確認)
- <疑問・反論>

# 答えてほしいこと
各対立点について:
1. 相手の主張のうち、認められる部分と認められない部分 (理由付き)
2. 自分の立場を 維持 / 修正 / 撤回 のどれにするか。理由と、決め手になった事実
3. 相手への再反論 (あれば)
立場を変えることは自由です。変えた場合は何が決め手だったかを書いてください。
```

- 立場の並びに人数・多数/少数は書かない (同調圧力を避ける)。自分がどの立場かは明示する
- モデレータの問いは「モデレータから」と明示して参加者の意見と混ぜない。答え方を押し付けない
- 対立・相違が1つもない場合は2周目をスキップしてよい (map.md に記録)。実行は「4. ラウンドの回し方」に従う (`r2-<name>.md`, `err-r2-<name>.log`)

### 8. 集約案 (`draft.md`) — モデレータ

2周目の返信を突き合わせ、全体の意見を集約する。**まだ最終出力ではない** (3周目のチェック対象):

```markdown
# 集約案 (中間成果物)
## 暫定結論
## 論点ごとの裁定
- <論点>: 採用した立場 — 理由。2周目で立場が変わった参加者の有無と、その理由の妥当性
- <論点>: まだ割れている — 両論と、どちらかに寄せられない理由
## 前提と未検証の仮定
## 残る不確実性
```

- 多数決で決めない。根拠の強さと事実確認で裁定する。裁定できない論点は「割れたまま」と正直に書く
- 判断材料が足りない論点は、何を確認すれば決まるかを書く
- モデレータ自身の言葉で書き、各回答の切り貼りで済ませない

### 9. 3周目 — 落とし穴チェック

集約案の全文を載せ、全参加者に壊しにいかせる。`<tmp>/r3-prompt.md`:

```markdown
以下は、ある議題についての複数参加者の意見を集約した案です。この案を壊しにいってください。

# 集約案
<draft.md 全文>

# チェックしてほしいこと
1. 論理の穴・飛躍 (根拠から結論が導けない箇所)
2. 見落としている観点・選択肢・リスク・ステークホルダー
3. 暗黙の前提のうち、崩れると結論が崩れるもの
4. この結論をひっくり返すような事実・論法 (あるなら具体的に)
5. 指摘の重要度 (致命/重要/軽微) を自分で付ける

# 出力形式
指摘ごとに: 重要度 / 内容 / 根拠 / それが正しければ結論がどう変わるか
```

実行は「4. ラウンドの回し方」に従う (`r3-<name>.md`, `err-r3-<name>.log`)。

### 10. 裁定と終了

3周目の指摘を1件ずつ裁定する:

- **妥当** → 集約案に組み込む (結論・論点・前提の修正)
- **過剰・誤り** → 理由を付けて棄却する。重要なものは「検討したが採用しなかった見解」として理由ごと最終出力に残す (ユーザーが判断できるように)
- **致命 (結論がひっくり返る)** → 握り潰さず、その論点を2周目と同じ形式で全参加者に投げ直して集約し直す。この追加ラウンドは**最大1回**。それでも決着しなければ結論を断定せず両論を残し、ユーザーに判断を委ねて終了する

致命の指摘がなければ、妥当な分を組み込んで終了する。

### 11. 最終出力 (`conclusion.md`)

```markdown
# 検討結果: <議題>

## 結論
<モデレータの言葉で。論点が複数なら箇条書き>

## 論点ごとの整理
- <論点>: <採用した立場> — 理由。検討したが採用しなかった見解とその理由

## 前提と未検証の仮定

## 残る不確実性と、次に必要な検証
```

成果物は tmp に `conclusion.md` として書き、そのパスをユーザーに報告する。リポジトリ内には書かない。チャットには結論の要点を短く書く。

**出力へのメタ情報混入は禁止 (fusion-review と同じ方針)**: 最終出力 (`conclusion.md` / チャットの報告文) に次を一切含めない:

- スキル名・手法名 (「discussion」「ディスカッション」「討論」「マルチモデル」「モデレータ」等)
- 討論者名 — llms.json の有効なエントリの `name` / `label`
- 参加人数 (「N人」「3モデル中2」)・合意状況 (「全員一致」「N対M」「単独意見」)
- モデル間の対立の記述 (「AはXと言ったがBはY」)
- 複数参加者の存在を匂わせる表現

書き出し前に、上記の語と llms.json の有効エントリ全ての `name` / `label` で最終出力を grep し、1件でもヒットしたら書き直す。中間成果物 (`r1-*`, `map.md`, `r2-*`, `draft.md`, `r3-*`) にはこれらの情報を書いてよい。

### 12. 後片付け

worktree を作った場合だけ:

```bash
git worktree remove --force <tmp>/discussion-wt
```

中間成果物は消さずに tmp に残す (経過を読み返せるように)。**ファイル名にモデル名が含まれるため、パスを報告文に列挙しない**。「中間結果は同じディレクトリに残してある」程度に留め、明示的に求められたときだけ具体名を出す。

## 注意

- **read-only**: 外部LLMにファイルを書かせない。llms.json の command は read-only 前提のフラグを維持する
- **コスト**: 呼ぶたびに (討論者数 × 3ラウンド) 分の API 料金が発生する。意見が割れる議題に絞る
- **モデレータの独立性**: 自分の結論を1周目のプロンプトに混ぜない。2周目の問いも結論を誘導しない (判断材料の確認に留める)
- **設定変更はレポ側で**: llms.json を `~/.claude/skills/` 配下の別ファイルとして作り直さない (Git 管理から外れる)
