# Test Generation

テストコードを書く前にプランを作り、プランに基づいてテストを書き、意味のあるテストだけが残っているかを検証する。

いきなりテストを書くと、カバレッジだけ満たす中身のないテストや、モックの設定をなぞるだけのテストが混ざる。プラン → テスト → 検証の順に進めることで、各テストが「何を保証しているのか」に答えられる状態を保つ。

## Workflow

### Step 0: コンテキスト収集

並行して調べる:

- テスト対象 (SUT) のコードを全体を読む
- 呼び出し側のコードを読み、実際の使われ方（渡される入力の範囲、期待される動作）を把握する
- リポジトリの既存テストから framework・命名規約・ファイル配置・assertion style を確認する（package.json / pyproject.toml / go.mod 等から test runner を特定）
- 対象に既にテストがある場合は、追加か修正かを判断する

### Step 1: テストプラン作成

テストコードを書く前に、プランを `/tmp/test-plan/<対象名>.md` に書く。リポジトリにはコミットしない一時ファイルで良い。

#### プラン.概要

そのコードが何を目的としたコードなのかを書く:

- 何を保証したいのか（仕様・不変条件・契約）
- 正常系で何が起き、異常系・エッジケースでどう扱われるべきか
- 外部依存（DB・API・時計・乱数）と、その扱い

このセクションはテストの取捨選択の基準になる。後で「このテストは概要のどの保証を確認しているか」に答えられないテストは書かない。

#### プラン.観点と要点

必要な観点を洗い出し、観点ごとにケース表を書く。各観点には「なぜ必要か」を 1 行で添える。

- **正常系**: 代表的な入力と期待出力
- **異常系・エッジケース**: 不正入力・空・null/undefined・巨大入力・同時実行
- **境界値分析**: 順序・サイズ・回数・日付など、順序や範囲が意味を持つ全てのパラメータについて min / min+1 / 代表値 / max-1 / max / 範囲外
- **decision table**: 複数条件の組み合わせで挙動が分かれる処理は、条件 → 結果の表を作る。**同じ結果に至る行は条件列をまとめて圧縮する。全組み合わせの列挙はしない**
- **網羅テスト**: 定義域が小さい有限集合（enum・ステータス遷移など）は全列挙する。定義域が大きい場合は代表値 + 境界値に絞る

ケース表の行数が爆発しそうなら、この段階で圧縮する（Step 3 ではなくここで判断する）。

### Step 2: テストコードを書く

- ケース表の各行が 1 テストケース。**表に無いケースは思いつきで足さない**
- リポジトリの既存テストの規約に従う（framework・配置・命名・describe/it 構造）
- テスト名は「何を保証しているか」が読み取れる名前にする（例: `上限を超えたリクエストは429を返す`）
- 外部依存のモックは SUT の挙動を見るための手段としてのみ使う

### Step 3: 実行と検証

テストを実行して all green を確認する。失敗した場合は、テスト側の想定間違いか SUT のバグかを切り分ける。SUT のバグなら安易に直さず、内容を報告して指示を仰ぐ。

その後、意味のないテストが無いかセルフレビューする:

1. **宣言的な定数のテスト**: `expect(MAX_RETRIES).toBe(3)` のように、実装の写しにすぎない assertion は無いか。定数の値そのものではなく、その定数を使った挙動（リトライ回数・しきい値での分岐）をテストする
2. **モックに対するテスト**: モックが返す値をそのまま assert していないか。mock で SUT を孤立させ、SUT の出力・状態・相互作用を assert する。「mock returns 42 → result が 42」で SUT が素通しの場合、それは mock のテストであり SUT のテストではないので削除する
3. **組み合わせ爆発**: ケース数が観点に対して異常に多い場合、decision table で行をマージするか代表値に絞る。パラメタライズで機械的にデカルト積を生成しない

最終基準: 全てのテストが「プラン.概要のどの保証を、プラン.観点のどの観点で確認しているか」に答えられること。答えられないテストは削除する。

### Step 4: 報告

以下をユーザーに報告する:

- テスト実行結果（pass/fail 数、失敗があれば内容）
- プランの観点と実装したテストの対応
- セルフレビューで削除した meaningless テストと理由

## Language

テストコードの記述言語（テスト名・コメント）は、明示的な指定がない限り、そのリポジトリの既存テストに従う。
