# deep-review — 5観点並列レビュー

同じ差分を**5つの異なるレンズ**を持つサブエージェントに並列でレビューさせ、集まった指摘を親エージェント (このセッション) が1件ずつ検証・裁定して統合する。単一の頭で順番に見ると必ず抜ける「差分の外」「異常系」「書かれなかったテスト」を、専用の目で埋めるのが目的。

5つに分ける基準はチェック項目ではなく**差分の読み方 (モード)**。項目で割ると視点が発散せず、担当表を配っただけになる:

| # | 観点 | 読み方のモード |
|---|---|---|
| 1 | 実装・コードベース整合性 | **横に読む** — 差分を既存コードと突き合わせる |
| 2 | 意図・設計判断 | **上流を読む** — 差分を要求と突き合わせる |
| 3 | 正しさ・テスト | **敵対的に読む** — 壊れる入力を作りにいく |
| 4 | ランタイム品質 | **時間軸で読む** — 本番で走らせた姿を想像する |
| 5 | セキュリティ | **悪意で読む** — 攻撃者の立場に立つ |

`fusion-review` が「複数モデル × 同一観点」なのに対し、これは「単一モデル × 複数観点」。役割が直交するので使い分ける。

## 実行手順

### Step 1: レビュー対象と出力モードを決める

**引数・文脈から出力モードを読み取る**。ここを間違えると成果物が届かないので最初に確定させる:

| 文脈のシグナル | 出力モード | 成果物 |
|---|---|---|
| PR番号 (`123` / `#123`) / PR URL が渡された | **PRモード** | PR の該当行へインラインコメント + 本文にサマリー |
| 「mdにまとめて」「レポートで」「ファイルに出して」 | **レポートモード** | tmp に `deep-review.md` を書き出してパスを報告 |
| 「そのまま修正して」「直して」「fixして」 | **修正モード** | リポジトリを直接修正 |
| どれとも取れない / 指定なし | **レポートモード** | 同上 |

判定に迷う組み合わせ (PR URL + 「修正して」など) はユーザーに確認する。**推測で PR に書き込んだり、リポジトリを書き換えたりしない。**

**レビュー対象**:

| 引数 | 対象 |
|---|---|
| PR番号 / URL | `gh pr view --json title,body,commits,files,closingIssuesReferences` + `gh pr diff` |
| なし | 未コミット変更 (`git diff HEAD` + untracked)。空なら `git diff main...HEAD` |

PR の場合は `closingIssuesReferences` の Issue も `gh issue view` で取得する (観点2の判定材料になる)。

### Step 2: worktree を用意する

**差分テキストだけを渡してはいけない。** DRY・慣習追従・影響範囲は、コード全体が無いと原理的に判定できない。レビュー対象コードが全体として存在する worktree を作り、各エージェントにそこを探索させる:

```bash
# PRモード
git fetch origin pull/<N>/head
git worktree add --detach <tmp>/deep-review-wt FETCH_HEAD

# ローカル差分
git worktree add --detach <tmp>/deep-review-wt HEAD
git diff HEAD | git -C <tmp>/deep-review-wt apply
git ls-files --others --exclude-standard | while read -r f; do
  mkdir -p "<tmp>/deep-review-wt/$(dirname "$f")" && cp "$f" "<tmp>/deep-review-wt/$f"
done
```

`<tmp>` はセッションの scratchpad (なければ `/tmp`)。**修正モードでも修正は worktree ではなく元の作業ツリーに対して行う** (worktree は使い捨ての調査環境)。

### Step 3: ガイドラインを収集する

worktree とユーザー環境から、レビュー基準になるものを集める:

- リポジトリの `CLAUDE.md`、`.claude/rules/`、`CONTRIBUTING.md`、`docs/` 配下のスタイルガイド・ADR
- ユーザーのグローバルルール `~/.claude/rules/`
- lint / formatter 設定 (`.eslintrc*`, `biome.json`, `ruff.toml`, `.prettierrc*`, `.editorconfig`) — 明文化された慣習

要点はプロンプトに直接貼る。長大なものはパスだけ示して worktree 内で読ませる。何も無ければ「明文化されたガイドラインなし。既存コードの慣習を基準とする」と明記する。

### Step 4: 5体を並列起動する

**1つのアシスタントメッセージに5つの `Agent` 呼び出しをまとめる** (逐次起動しない)。`subagent_type: "general-purpose"`、cwd は worktree。

#### 成果物は中間ファイルに吐かせる

**サブエージェントは自分の手で成果物を作らない。** レビュー結果を `<tmp>/review-<slug>.md` に書き出すところまでが仕事で、リポジトリの修正・PRへのコメント投稿・最終レポートの生成は**すべて親エージェントが中間ファイルを読んでから行う**:

| # | 観点 | 出力ファイル |
|---|---|---|
| 1 | 実装・コードベース整合性 | `<tmp>/review-impl.md` |
| 2 | 意図・設計判断 | `<tmp>/review-intent.md` |
| 3 | 正しさ・テスト | `<tmp>/review-correctness.md` |
| 4 | ランタイム品質 | `<tmp>/review-runtime.md` |
| 5 | セキュリティ | `<tmp>/review-security.md` |

サブエージェントの**返り値は3行の要約だけ**にする (ファイルの中身を繰り返させない)。指摘の本体はファイルにしか存在せず、親はそれを Read して裁定する。こうすることで親のコンテキストが5本分のレビュー全文で埋まらず、裁定と修正に使える余地が残る。

#### コンテキストを継承させない (このスキルの肝)

5体を分ける目的は**視点を発散させること**。親のコンテキストが流れ込むと全員が親と同じ見立てをなぞり、5体起動した意味が消える。以下を厳守する:

- **`subagent_type: "fork"` を使わない。** fork は親の会話コンテキストを丸ごと継承するため、視点が確実に収束する。必ず新規コンテキストの `general-purpose` を使う
- **親が先に自分のレビュー結論を作らない。** Step 4 より前に差分の良し悪しを判断し始めない。持ってしまった見立ては裁定 (Step 5) まで出さない
- **プロンプトに親の見解・仮説・懸念を書かない。** 「ここが怪しいので重点的に見て」は禁止。渡すのは客観的な入力 (diff / worktree パス / ガイドライン / PR本文・Issue本文) だけにする
- **会話履歴を渡さない。** 「背景」に入れるのはユーザーの依頼内容のうちレビューに必要な事実のみ。それまでのやり取りの要約や、実装時の議論・意図の説明を入れない (実装者の言い分を先に読ませると批判の刃が鈍る)
- **5体のプロンプトは「観点」セクションだけが異なり、他はすべて同一テキストにする。** 観点以外に差を付けると、どの差が結果を動かしたのか分からなくなる
- **エージェント同士の結果を共有しない。** 相互参照させず、全員に同じ差分をゼロから見せる。重複は Step 5 で親が潰す前提なので、重複を恐れて担当範囲を狭めない

各エージェントに渡す共通プロンプト:

```markdown
あなたは「<観点名>」専門のコードレビュアーです。この観点だけを担当し、他観点の指摘は書かないこと。

# レビュー対象
<diff 全文。巨大な場合は変更ファイル一覧 + 主要差分に絞り、残りは worktree で読ませる>

コード全体は <worktree絶対パス> にチェックアウト済み。
差分だけで判断せず、必要に応じてリポジトリ内を読んで判断すること。

# 禁止事項 (厳守)
- リポジトリ (worktree 含む) は**読み取り専用**。ソースを一切変更しないこと
- git は読み取り系コマンドのみ (log / grep / blame / show)。commit / push / checkout をしない
- **PR へのコメント投稿をしないこと** (gh pr review / gh pr comment / gh api への書き込み一切)
- 書き込んでよいのは下記の出力ファイル1本だけ

修正・PRコメント・最終レポートの生成はすべて親エージェントが行う。
あなたの仕事は出力ファイルを書くところまで。

# 背景
<PR本文 / 紐づくIssue本文 / ユーザーの依頼内容>

# このプロジェクトのガイドライン
<Step 3 で集めた要点。長いものはパスを提示>

# あなたの観点
<下表の「見るもの」を展開。【】で区切られたパートはすべて担当範囲>

# 出力先 (必ずこのファイルに Write すること)
<tmp>/review-<slug>.md

# 出力ファイルの中身
## <観点名>

### 指摘 (重要な順、最大12件)
- [CRITICAL|HIGH|MEDIUM|LOW] path/to/file.ts:123 — <問題点>
  - 根拠: <コード上の事実。親エージェントが検証できるよう、行番号・関数名・実際の値で書く>
  - 修正案: <具体案>

### 確認したが問題なし
- <何を見て問題なしと判断したか。1項目1行>

**観点が【】で複数パートに分かれている場合、パートごとに指摘と「問題なし」を書き分けること。
片方だけ埋めて終わらない。指摘が出しやすい方に流れるのが最大の失敗パターン。**

推測だけで指摘を書かないこと。「〜かもしれない」で終わる指摘は出さず、
コードを読んで裏を取るか、出さないかのどちらかにする。
件数を稼ぐ必要はない。指摘ゼロでよい。指摘ゼロでもファイルは必ず作ること。

# 返り値 (チャットに返す内容)
ファイルの中身を繰り返さないこと。以下3行だけを返す:
- 書き出したファイルの絶対パス
- 指摘件数と重要度の内訳 (例: 7件 / CRITICAL 1, HIGH 2, MEDIUM 3, LOW 1)
- 担当パートのうち未確認で終わったものがあればその名前 (なければ「なし」)
```

### 5つの観点

| # | 観点 | 見るもの |
|---|---|---|
| 1 | **実装・コードベース整合性** | 【差分の中】ガイドライン・lint設定違反。命名/ディレクトリ構成/エラーハンドリング/ログ書式が既存パターンと整合するか。DRY (既存ユーティリティの再実装・差分内の重複)。**worktree 内の類似コードを検索し「既存はこう書いている」と対比した根拠を出す**。UIファイルが含まれる場合は a11y (ラベル/フォーカス/コントラスト) と i18n (ハードコード文言) も見る<br>【差分の外 — 必ず実施】変更/削除されたシンボルの**呼び出し元を worktree 全体で Grep して洗い出す**。公開API・レスポンス形状・DBスキーマの破壊的変更。マイグレーションがローリングデプロイ中の新旧コード共存に耐えるか、ロック・バックフィルの危険。強制アップデートできないクライアントとのバージョンスキュー。環境変数・シークレット・設定の追加漏れ、ロールバック可能性 |
| 2 | **意図・設計判断** | 【要求との一致】PR本文 / 紐づくIssue / `docs/` の仕様からの逸脱 (過剰実装・実装漏れ・解釈違い)。受け入れ条件を満たしているか。スコープ外の変更・デバッグコード残骸の混入。この変更で陳腐化する doc/README/OpenAPI/CHANGELOG がないか<br>【手段の妥当性】採られた実装以外の選択肢を2〜3案挙げ、トレードオフを比較して推奨を出す。リポジトリ内に同種の問題を別方法で解いている先行事例がないか (あるならそちらに寄せるべきか)。新規依存を足しているなら既存依存・標準ライブラリで足りないか。**代替案は「指摘」ではなく提案として重要度を付けずに出す。「現状の実装で妥当」と結論してよく、無理に代替案を作らない** |
| 3 | **正しさ・テスト** | null/undefined、境界値、空コレクション、0/負値、オーバーフロー、丸め、タイムゾーン、文字エンコーディング。分岐の網羅、早期returnの抜け、握り潰された例外。**見つけたエッジケースごとに、それを検証するテストが存在するか照合する**。テストが実装の現状をなぞっているだけ (バグを固定化) でないか。モックの振り付け検証になっていないか。時刻/乱数/ネットワーク依存で不安定でないか |
| 4 | **ランタイム品質** | 【性能】N+1、ループ内のI/O、不要な再計算、O(n²)。データ量が10倍・100倍になった時の挙動。フロントエンドの不要な再レンダリング・メモ化漏れ・同期的な重い処理・バンドルサイズ。DBのインデックス有無・フルスキャン・ロック。キャッシュが効いているか<br>【異常系・可観測性】外部依存 (API/DB/キュー) が落ちた・遅い時の挙動。タイムアウト、リトライ (指数バックオフ)、サーキットブレーカ。冪等性、二重実行、リトライ安全性。トランザクション境界、部分失敗時の状態の壊れ方、レースコンディション。エラーがユーザーにどう見えるか (握り潰し・生スタックトレース露出)。**本番でこの経路の障害を、ログ/メトリクス/トレースだけで特定できるか** |
| 5 | **セキュリティ** | 認証・認可 (IDOR、テナント/ユーザー境界の越境)。入力検証、インジェクション (SQL/コマンド/パス/テンプレート)、XSS/CSRF。シークレット・トークンのハードコード、ログ・エラーメッセージへのPII/認証情報の流出。権限昇格、安全でないデシリアライズ、脆弱な暗号・乱数。新規依存のCVE・メンテ状況・ライセンス |

観点は**常時この5つを固定で起動する**。差分の内容によって増減させない (小さい差分では各エージェントが「指摘なし」を返すだけで済む)。

**統合観点 (1・2・4) の偏りに注意する。** 指摘が出しやすい方 (観点1なら規約・DRY、観点4なら性能) に寄って、もう片方が省略されるのが典型的な失敗。特に**観点1の「呼び出し元の Grep 洗い出し」は結果が空でも実施したこと自体を出力させる**。報告に該当パートが無ければ、親エージェントはそのパートを未実施とみなして追加で確認する。

### Step 5: 裁定 — 親エージェントが重複と誤検知を判定する

**この工程をサブエージェントに委譲しない。**

まず `<tmp>/review-*.md` 5本を親エージェントが **Read する**。サブエージェントの返り値は3行の要約でしかなく、**指摘の本体はファイルにしかない**。要約だけで裁定や修正に進んではならない。

ファイルが存在しない・空・形式が壊れているエージェントは**リトライせずスキップ**し、その観点を未カバーとして最終報告に明記する。

読み込んだ5体分の指摘 (誤検知込みで15〜30件になる) を、親エージェントが1件ずつコードに当たって処理する:

1. **重複統合** — 同一 file:line 近傍かつ同趣旨の指摘を1件にマージする。重要度は高い方を採用し、根拠は情報量の多い方を残す。観点をまたいだ重複 (観点4と観点3が同じ行を別理由で指摘、など) は、理由が異なるなら**統合せず両方残す**
2. **誤検知の棄却** — 各指摘の「根拠」を**実際にコードを読んで検証する**。根拠が確認できない、既に別の場所で対処済み、そのコードパスに到達しない、前提が事実と違う、といったものは棄却する。エージェントの断定を鵜呑みにしない
3. **重要度の再評価** — 各エージェントは自分の観点の中で重要度を付けているため、全体で見ると過大・過小になる。差分全体のリスクの中で付け直す
4. **カバレッジ確認** — 各報告に【】パートが揃っているか見る。欠けているパートは親が自分で確認して埋める
5. **棄却したものは捨てずに記録** — 理由付きで別セクションにまとめ、チャットでの報告にのみ含める (PR・レポートには出さない)

裁定は必ず親エージェント自身の言葉で書く。5体の出力の切り貼りで済ませない。

### Step 6: 出力 — Step 1 で決めたモードで成果物を出す

#### PRモード

統合結果を**1つのレビュー**として投稿する。行を特定できる指摘はインラインコメント、特定できない指摘とサマリーは本文に入れる:

```bash
gh api repos/{owner}/{repo}/pulls/{number}/reviews --input review.json
```

```json
{
  "commit_id": "<PRのheadのSHA>",
  "event": "COMMENT",
  "body": "<全体評価 + 行を特定できない指摘 + 代替案>",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "side": "RIGHT", "body": "[HIGH] 内容\n\n根拠: ...\n\n修正案: ..." }
  ]
}
```

- `event` は `COMMENT` 固定 (approve / request changes の判断は人間に残す)
- 投稿後にレビューURLを報告する

#### レポートモード

`<tmp>/deep-review.md` に書き出し、パスを報告する。**リポジトリ内には書かない。**

```markdown
# Deep Review

## 全体評価
<数行。品質・リスクの所感、このままマージ可能か / 修正必須か>

## 指摘 (重要度順)
### [CRITICAL] path/to/file.ts:42 — <見出し>
<内容 / 根拠 / 修正案>

## 代替案 (観点2)
<採用/不採用の判断材料として。重要度は付けない>
```

#### 修正モード

採用した指摘のうち、**設計変更を伴わないもの**を元の作業ツリーに対して修正する:

- 修正対象: バグ・エッジケース漏れ・セキュリティホール・規約違反・テスト追加など、局所的に閉じるもの
- **修正しないもの**: 設計変更・大きなリファクタリング・代替案 (観点2) の採用。これらは提案に留めてユーザーに判断を仰ぐ (迷ったら修正しない)
- 修正後、対象リポジトリの lint / テスト (`CLAUDE.md` に記載のコマンド、なければ検出) を実行して PASS を確認する
- **自動でコミットしない。** 修正内容の一覧を報告し、コミットはユーザーに委ねる

### Step 7: 後片付け

```bash
git worktree remove --force <tmp>/deep-review-wt
```

**中間成果物 `<tmp>/review-*.md` は消さない。** 観点別の生レビューを読み返せるよう残し、パスを報告に併記する (裁定で棄却した指摘の根拠を後から追えるようにするため)。

いずれのモードでも、最後にチャットで以下を報告する:

- 採用した指摘の件数と重要度の内訳
- 棄却した指摘とその理由 (Step 5-5)
- 未カバーで終わった観点があればその名前
- モード別の成果物 (レビューURL / レポートのパス / 修正したファイル一覧)
- 中間成果物 `<tmp>/review-*.md` のパス

## Rules

- **5観点は固定。** 差分の大小で減らさない。観点を減らすと「そこは誰も見ていない」状態が黙って発生する
- **5体は1メッセージで並列起動する。** 逐次起動は待ち時間が5倍になるだけで精度は上がらない
- **各エージェントは新規コンテキストで起動する (`fork` 禁止)。** 親の見立て・会話履歴・他エージェントの結果を渡さない。視点の発散がこのスキルの価値そのもので、コンテキスト共有はそれを直接壊す
- **統合観点は【】パートごとに出力を分けさせる。** 片方に流れて片方が空になるのを防ぐ。空のパートは親が埋める
- **サブエージェントは成果物を作らない。** 書き込みを許すのは `<tmp>/review-<slug>.md` 1本だけ。リポジトリの修正・PRコメント投稿・最終レポート生成は**すべて親エージェントが中間ファイルを読んでから**行う。サブエージェントに直接やらせると、誰も検証していない指摘がそのまま外に出る
- **親は中間ファイルを Read してから裁定する。** サブエージェントの返り値 (3行要約) だけで修正やコメントに進まない。指摘の本体はファイルにしかない
- **裁定は親エージェントの仕事。** サブエージェントに「他のエージェントの指摘をレビューさせる」構成にしない (誰も検証していない指摘の山になる)
- **指摘には必ず `file:line` と検証可能な根拠を付けさせる。** 根拠が無い指摘は裁定で棄却する
- **差分だけで判断させない。** 必ず worktree を渡す。特に観点1 (慣習・DRY・呼び出し元) は差分だけでは判定不能
- **出力モードを推測で決めない。** PR書き込みとリポジトリ修正は取り返しがつきにくい。文脈が曖昧なら確認する
- **PR には `event: COMMENT` のみ。** approve / request changes は人間の判断
- 修正モードで自動コミット・自動pushしない
- コスト: 5体のサブエージェントを起動するので安くない。軽い確認には `local-reviewer` / `pr-reviewer` エージェントを使う

## 関連スキル

| したいこと | 使うもの |
|---|---|
| 単一モデル × 5観点で深く見る | **/deep-review** (これ) |
| 複数モデルの意見を突き合わせる | `/fusion-review` |
| レビュー待ちPRを見つけて捌く (merge/close まで) | `/dev-pr-review` |
| 未コミット変更をサッと見る | `local-reviewer` エージェント |
| 同じ作業を多数ファイルに横展開する | `/fanout` |
